# Adaptive 시각 탐색 설계 초안

목표는 질문의 역할과 근거 상태를 이용해 다음 crop, 탐색 전환, 종료를 결정하는 것이다.
이 초안의 효과는 아직 검증하지 않았다. 기존 Greedy/MCMC/Lookahead와 실행 중인 실험은 변경하지 않는다.
겹침 병합, 큰 면적 기각, 중심점 거리 기반 전처리는 보류한다.

## 계획과 상태

계획은 **역할·근거·의존 관계 그래프**, 후보는 **역할에 연결된 위치 가설**, 관측은 **출처가 있는 기록**으로 나눈다.
하나의 후보가 여러 역할에 도움을 줄 수 있고, 한 역할에도 여러 후보가 존재할 수 있다.
역할 수를 proposal 수와 같게 두지 않는다. 우선순위 큐는 후보의 실행 순서를 정하는 용도이며, 계획 그래프를 대신하지 않는다.

예: “빨간 배낭을 멘 사람의 손목시계는 무슨 색인가?”

| 역할 | 확인할 근거 | 정체성·결론을 확정하기 위한 선행 조건 |
| --- | --- | --- |
| `bag` 기준 대상 | 빨간 배낭의 위치와 외형 | 없음 |
| `wearer` 참조 대상 | 해당 배낭을 멘 사람이라는 연결 | `bag`의 식별 |
| `watch` 응답 대상 | 그 사람의 시계라는 연결과 판독 가능한 색 | `wearer`의 식별 |
| 최종 추론 | 관측된 색을 보기와 대응 | `watch`의 색 근거 |

사람 후보는 배낭을 찾기 전에도 제안할 수 있다. 선행 조건은 후보 생성을 금지하는 조건이 아니라,
그 후보가 질문의 사람이라고 **결부시키기 위한 조건**이다. “빗자루는 의자의 어느 쪽인가?”라면
빗자루와 의자는 독립적으로 탐색하고, 위치 관계 판단이 두 위치에 의존한다.

| 상태 요소 | 최소 정보 |
| --- | --- |
| 역할 | ID, 대상 역할, 확인할 근거, 중요도, 선행 역할 ID |
| 후보 | ID, 이미지 참조, 정규화 좌표, 연결 역할 ID, 확인할 근거, 우선도, 분기 |
| 관측 | 실제 이미지/crop 출처, VLM 보고, 관련 역할과 가설, 진전·충돌 보고 |
| 실행 상태 | 현재 계획, 후보별 사용 예산·보류 여부, 관측 이력, 총 사용량, 종료 이유 |

`expected_evidence`는 확인할 항목이며, 관측한 사실이 아니다. VLM의 관측·근거 충족 판단도
검증된 정답으로 취급하지 않고 보고와 출처를 보존한다. 미해결·부분 확보·충돌을 구분한다.
질문마다 별도 상태를 생성하여 서로 다른 문항의 계획과 이력이 섞이지 않도록 한다.

## Plain-language pseudocode

```text
문제·보기·원본 이미지를 읽고 역할, 확인할 근거, 선행 조건을 계획한다.
원본에서 얻은 관측 보고를 출처와 함께 기록한다.
원본 근거가 충분하다는 보고가 있으면 crop 없이 최종 추론으로 간다.

추가 근거가 필요한 역할에 후보를 제안한다.
각 후보를 이미지 참조, 좌표, 역할, 확인할 근거에 연결한다.

탐색 예산이 남고 추가 근거가 필요한 동안:
    중요도, 선행 조건의 병목, 현재 근거 상태로 후보 순서를 정한다.
    후보 하나를 고르고 짧은 분기 예산을 적용한다.
    실제 crop 하나만 실행하고 관측 보고와 출처를 기록한다.
    역할의 근거 상태, 충돌, 위치·정체성 가설을 갱신한다.

    전체 근거가 충분하다는 보고가 있으면 탐색을 종료한다.
    역할이 해결되었으면 다른 필요한 역할로 전환한다.
    진전이 없거나 분기 예산을 소진하면 해당 분기를 보류한다.
    중요한 병목에서 진전이 있을 때만 제한된 추가 예산을 준다.

    필요하면 계획과 후보를 수정한다.
    참조 무결성과 의존 관계의 순환 여부를 검사하고 다시 순서를 정한다.

관측 이력과 관련 중간 추론을 조합하여 최종 보기를 선택한다.
남은 근거 부족·충돌과 종료 이유도 기록한다.
```

## 예산과 전환

- 기본 분기 예산은 짧게 둔다. 상위 역할·병목이라는 이유만으로 무조건 연장하지 않는다.
- 분기의 후속 후보는 `branch_id`를 공유하고, 중첩 crop은 이미지 출처의 분기를 상속한다.
- 추가 예산에는 분기별 상한과 전체 상한이 있다. 실패한 후보를 반복 확대하는 고착을 제한한다.
- 각 관측 뒤 재정렬하므로 처음 정한 순서를 끝까지 따르지 않는다. 새 가설이나 충돌로 계획도 수정할 수 있다.
- 총 crop·planner 호출 상한과 최종 응답용 여유를 구분한다. 실제 API 비용과 달러 상한은 외부 client/원장이 관리한다.
- 정상 종료와 예상한 crop 실패는 관측 이력·종료 이유에 기록한다. API·계량 오류는 상위로 전파하며,
  오류 시 영속 기록과 재개는 계량 하네스가 담당한다.

## 코드 연결

`AdaptivePolicy.run(question, original_image_key, backend, executor) -> Result`는 매번 별도
`CaseState`를 만든다. `Role`/`Plan`, `Candidate`, `Claim`/`Report`, `Observation`에 상태를 기록하고,
각 단계에서 heap을 다시 만들어 후보를 선택한다. `Role.requires_for_binding`은 확인 보고를
결부시키는 조건이며 후보의 탐색 가능 여부를 제한하지 않는다.

`Backend`의 비동기 계약은 `plan(question, original_image_key) -> Plan`,
`propose(state) -> Sequence[Candidate]`, `observe(state, candidate, cropped_image_key) -> Report`,
`finalize(state) -> str`이다. 별도로 주입하는 `CropExecutor(candidate) -> image_key`가 실제 crop을
하나 실행한다. `Report`는 역할별 주장, 새 후보, 선택적 계획 수정을 전달한다.
구체적인 VLM 프롬프트·출력 schema adapter는 외부 backend의 책임이며 이 초안은 모델 입출력을 직접 실행하지 않는다.
Backend에는 상태 복사본을 전달한다. 예상한 도구 실패만 `CropError`로 반환하며, API·계량 오류는
상위 하네스로 전파한다. 계획이 바뀌면 관련 근거 상태와 후보를 무효화하고 원래 기록을 보존한다.

`Limits`는 crop 수, backend 호출 수(마지막 응답용 1회 예약), 분기·방문 예산을 제한한다.
호출 수 제한은 달러 비용을 보장하지 않는다. 실제 비용 예약과 공용 원장은 기존 계량 backend에서 적용해야 한다.
모델 호출 상한은 논리 callback 수이며, 하네스의 전송·형식 재시도는 별도 물리 요청으로 기록하고 비용에 포함한다.

기존 정책의 `get_action(...) -> Bbox`는 현재 부모 이미지에 대한 좌표만 반환한다.
이 설계는 원본 또는 다른 관측 이미지로 전환할 수 있어 **이미지 참조와 좌표**를 함께 전달하는
adapter가 필요하다. 기존 정책을 그대로 교체하는 drop-in 연결이나 registry 자동 등록은 하지 않는다.
초안 controller의 검증은 가짜 backend로 수행하며, 이 파일 작성만으로 유료 실험을 시작하지 않는다.

```python
policy = AdaptivePolicy(Limits(max_steps=10, max_model_calls=24))
result = await policy.run(question, "original", backend, crop_executor)
# result.answer: 최종 답변 / result.state: 계획·후보·관측·분기 사용량
```
